# Part 1 — Return-Risk Prediction

## 1. Overview

Part 1 builds the order-level machine-learning component of the **Flipkart Order Intelligence & Support Assistant**.

The objective is to predict the probability that an order will be returned using order, customer, payment, product, delivery, and rating-related features.

The final artifact is a tuned **Random Forest classification pipeline**. Part 3 loads this exact saved model and uses its real `predict_proba()` output when a support request asks for return-risk analysis.

The Part 1 workflow is:

```text
Generate synthetic order data
        ↓
Verify dataset
        ↓
Preprocess features
        ↓
Dummy baseline
        ↓
Logistic Regression baseline
        ↓
Random Forest + GridSearchCV
        ↓
Random Forest probability threshold sweep
        ↓
Save final model + t*_rf
        ↓
Part 3 return-risk tool
```

The assessment specifically requires the saved artifact to be the tuned Random Forest pipeline rather than the Logistic Regression model, and requires `t*_rf` to be calculated from the Random Forest's own test-set probabilities.

## 3. Dataset

### Dataset generation

The dataset is generated by:

```text
Part-1/generate_orders.py
```

Run it from the repository root:

```powershell
python "Part-1/generate_orders.py"
```

This creates:

```text
orders_dataset.csv
```

The required dataset contains:

* 6,000 rows
* 13 columns
* order-level information
* binary `returned` target
* missing values in `rating_given`

The assessment specifies that the generated dataset must contain exactly 6,000 rows and 13 columns, with an overall return rate between 18% and 27% and missing `rating_given` values between 8% and 18%.

### Dataset fields

The main predictive fields are:

```text
order_id
product_category
price_inr
discount_pct
payment_method
customer_tenure_days
num_previous_orders
num_previous_returns
delivery_distance_km
delivery_days
is_weekend_order
rating_given
returned
```

The missingness of `rating_given` is treated as **MAR (Missing At Random)** because the generation process makes missingness depend on the observed `payment_method` variable rather than on the unobserved rating itself. The assessment explicitly requires this distinction.

## 5. Baseline Model

Run:

```powershell
python "Part-1/baseline_model.py"
```

The DummyClassifier provides a deliberately weak reference point.

The important lesson is that a classifier can have apparently acceptable accuracy while producing almost no useful positive-class detection. In this project the baseline positive-class F1 is expected to be approximately:

```text
F1(returned=1) = 0.0
```

This demonstrates the **high-accuracy / zero-recall trap**.

---

## 6. Logistic Regression

Run:

```powershell
python "Part-1/logistic_model.py"
```

Logistic Regression is used as a simpler baseline.

The workflow includes a probability-threshold sweep rather than relying only on the default classification threshold.

The purpose is to demonstrate the precision/recall trade-off for return detection.

The Logistic Regression threshold is **not** reused by Part 3.

Part 3 uses the threshold calculated from the Random Forest itself.

---

## 7. Final Random Forest

Run:

```powershell
python "Part-1/random_forest_model.py"
```

The script:

1. Loads the generated order dataset.
2. Builds the preprocessing pipeline.
3. Trains a Random Forest classifier.
4. Uses GridSearchCV for model selection.
5. Evaluates the selected model.
6. Calculates probabilities using:

```python
model.predict_proba(X_test)
```

7. Performs a threshold sweep.
8. Selects the F1-maximising Random Forest threshold:

```text
t*_rf
```

9. Saves the complete fitted pipeline.

The final model is saved as:

```text
models/return_risk_model.pkl
```

The threshold metadata is saved as:

```text
models/return_risk_threshold.json
```

The threshold must be the F1-maximising threshold from the **Random Forest's own probability output**, not the Logistic Regression threshold.

---

## 8. Why `t*_rf` Matters

Part 3 does not use an arbitrary probability such as:

```text
0.30
0.50
0.60
```

as a universal risk boundary.

Instead, the Random Forest's own calibrated test-set probability scale is used.

Conceptually:

```text
Random Forest
      ↓
predict_proba()
      ↓
probability for returned=1
      ↓
threshold sweep
      ↓
best F1
      ↓
t*_rf
```

The saved value is loaded from:

```text
models/return_risk_threshold.json
```

This keeps Part 3 synchronized with the actual Part 1 model.

Part 1 also investigates which variables contribute to return prediction.

## 10. Example: What Happens When a User Asks for Return Risk?

Suppose the user asks:

```text
Check the return risk for my order.

Price: ₹2499
Discount: 20%
Customer tenure: 180 days
Previous orders: 8
Previous returns: 1
Delivery distance: 12.5 km
Delivery days: 4
Weekend order: No
Rating: 4
Category: Electronics
Payment: UPI
```

The Part 1 model itself performs:

```text
User order features
        ↓
Pandas DataFrame
        ↓
Saved preprocessing pipeline
        ↓
Saved Random Forest
        ↓
predict_proba()
        ↓
Return probability
```

For example, the model may produce:

```text
Return probability: 0.31
```

Part 3 then compares that probability with the saved:

```text
t*_rf
```

and produces the appropriate risk bucket.

The exact probability must always come from the saved model; README examples must not be treated as hardcoded model outputs.

---

## 11. What If Information Is Missing?

If the Part 3 tool receives an incomplete order, for example:

```text
Price: ₹2499
Category: Electronics
Payment: UPI
```

but required model features are absent, the tool does not invent those values.

The request should instead be rejected or returned with a missing-feature error.

This protects the model from silently making a prediction using fabricated input.

## 14. Final Part 1 Findings

The project demonstrates that:

* Synthetic order data can be generated reproducibly.
* `rating_given` has informative missingness related to observed payment behavior.
* A dummy classifier is inadequate for return detection.
* Logistic Regression provides a useful baseline.
* Probability-threshold selection changes the precision/recall balance.
* Random Forest provides the final nonlinear model.
* The final model is saved as a complete preprocessing + model pipeline.
* `t*_rf` is calculated from the Random Forest itself.
* The saved model can be reused by Part 3 without retraining.

Part 1 therefore provides the **order-intelligence foundation** for the complete support assistant.
